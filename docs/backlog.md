## 다이어리 Phase 2 — 미디어 첨부 · 용량 한도

> 출처: 프론트 레포 다이어리 요청서 "Phase 2 예고" (2026-09-01 인계)
> 선행 작업: [21-diary.md](features/21-diary.md) (Phase 1 완료)
> 상태: ⬜ 미착수 — **별도 요청서를 받은 뒤 착수**

Phase 1은 텍스트 일기와 빠른 기록까지만 다뤘다. 사진·영상은 저장 비용과
동시성 문제가 텍스트와 성격이 완전히 달라 통째로 분리했다.

### 할 일

- [ ] **`DiaryMedia` 모델** — 사진·영상. `Diary` 1 : N, 업로드 상태(PENDING/CONFIRMED) 보유
- [ ] **용량 한도** — 월간 사용량 + 계정 누적 사용량, 구독 등급별로 상한이 다름
- [ ] **R2 Presigned URL 직접 업로드** — `reserve` → 클라이언트가 PUT → `confirm` 3단계.
      서버를 거치지 않고 R2로 직접 올린다. `storage.service.ts`의 `getUploadUrl()`이 **이미 구현되어 있음**
- [ ] **Redis 락** — 동시 업로드가 겹칠 때 한도 계산이 경합하지 않도록. 다이어리 빠른 기록에서
      쓴 `SELECT ... FOR UPDATE`와 달리, 한도는 여러 행에 걸친 집계라 분산 락이 필요하다
- [ ] **정리 스케줄러 2종**
  - PENDING 상태로 15분 넘게 남은 예약 → 취소 처리
  - R2에는 있는데 DB에 없는 고아 미디어 → 24시간 후 삭제
- [ ] **`GET /subscription/quota-plans`** — 등급별 한도표 (클라이언트가 업그레이드 유도 화면에 사용)
- [ ] **`calendar` 응답의 `hasMedia`를 실제 값으로 채우기** — Phase 1에서는 항상 `false`로 내려두었다.
      필드 자리를 미리 잡아뒀으므로 프론트 모델 변경은 필요 없다

### 착수 시 지켜야 할 Phase 1 결정

- **삭제 정책의 비대칭** — 일기 본문은 soft delete 30일 후 완전 삭제(복구 가능)지만,
  **첨부 미디어는 즉시 영구 삭제**한다. 텍스트는 복구 가치가 크고 저장 비용이 0에 가깝지만
  미디어는 정반대다. 일기를 삭제할 때 미디어를 함께 지울지, 복구 시 어떻게 되는지 명시할 것
- **하루 경계는 새벽 4시(KST)** — 월간 사용량 집계도 `diaryDateInKst()` 기준을 따라야
  캘린더·스트릭과 어긋나지 않는다
- **권한** — 그룹 일기의 미디어는 그룹원 전원이 추가·삭제할 수 있어야 한다
  ([group-permissions.md](maintenance/group-permissions.md)의 공통 규칙)
